# MariaDB Schema

KanbanBoard.Api now uses MariaDB through `MySql.EntityFrameworkCore`.
The application expects `ConnectionStrings__Kanban` to point at an existing database.

## Create Database

Create the database and user before the API or the scripts create the schema:

```sql
CREATE DATABASE kanban CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kanban'@'%' IDENTIFIED BY 'replace-with-secret';
GRANT ALL PRIVILEGES ON kanban.* TO 'kanban'@'%';
FLUSH PRIVILEGES;
```

Restrict the host portion of the user if your MariaDB topology allows it.

## Apply Schema

The API applies pending EF Core migrations on startup (`Database:MigrateOnStartup`, default `true`), so a database that already has `001` applied is brought up to date by deploying the new image. The connection's user therefore needs schema-change privileges on `kanban` (at least `ALTER`, plus `CREATE`, `INDEX`, `DROP` and `REFERENCES` for migrations that add tables, indexes or keys). The `GRANT ALL PRIVILEGES ON kanban.*` above covers this. See [deployment.md](deployment.md#schema-changes-on-deploy).

The checked-in scripts remain for bootstrapping a new database and for manual use (for example with `Database__MigrateOnStartup=false`). Run them in order:

```bash
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/001_initial_mariadb_schema.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/002_personal_access_token_scope.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/003_work_item_claim.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/004_work_item_dependencies.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/005_work_item_links.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/006_work_item_comment_author_and_idempotency_key.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/007_project_repository_and_idempotency_key.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/008_work_item_version_and_longer_labels.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/009_work_item_changes.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/010_create_idempotency_keys_and_epic_plan_imports.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/011_app_user_disabled_at.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/012_personal_access_token_admins.sql
mariadb -h HOST -P 3306 -u kanban -p kanban < deploy/sql/013_work_item_changes_item_index.sql
```

Each script records its migration id in `__EFMigrationsHistory`, so the API skips migrations already applied by hand. A test (`StartupMigrationTests.Deploy_sql_history_rows_match_every_ef_migration`) fails if the ids in `deploy/sql` drift from the migrations in `KanbanBoard.Api/Data/Migrations`; add a numbered script with each new migration.

`002` adds the `PersonalAccessTokens.Scope` column (`read` or `full`); existing tokens default to `full`. It is safe to re-run.

`003` adds the claim columns to `WorkItems`: `ClaimantUserId`, `ClaimantName`, `ClaimMarker` and `ClaimExpiresAtUtc`, all nullable, so existing items start unclaimed. `ClaimMarker` is `utf8mb4_bin` so markers compare byte for byte. `MySql.EntityFrameworkCore` leaves the collation out of the `ADD` it generates, so the migration (and the script) sets it with an explicit `MODIFY`. It is safe to re-run.

`004` adds the `WorkItemDependencies` table: one row per edge, `BlockedItemId` is blocked by `BlockerItemId`, with the pair as primary key. Both columns reference `WorkItems.Id` with `ON DELETE CASCADE`, so deleting a work item or its project removes its edges. It is safe to re-run.

The API serialises dependency adds with the MariaDB named lock `kanban_work_item_dependencies` (`GET_LOCK`, 10 s timeout), so the cycle check and the insert of two concurrent adds cannot interleave. It is held for one request and released on the same connection; `SELECT IS_USED_LOCK('kanban_work_item_dependencies')` shows a holder. An add that waits the full 10 s is refused with HTTP 503 and code `busy`, and writes nothing.

`005` adds the `WorkItemLinks` table: one row per external URL attached to a work item, with a `Kind` (`pr`, `branch` or `other`). `WorkItemId` references `WorkItems.Id` with `ON DELETE CASCADE`. `Url` holds up to 2048 characters, which is more than an index key can hold under `utf8mb4`, and the database's default collation would compare it ignoring case; so the API stores `UrlHash`, the SHA-256 of the URL in lowercase hex, and both the unique key (`WorkItemId`, `Kind`, `UrlHash`) and the lookup by URL (`IX_WorkItemLinks_UrlHash`) use the hash. A row whose `UrlHash` does not match its `Url` is never found by URL, so do not insert links by hand. It is safe to re-run.

The API starts every link add and remove with the `UPDATE` that stamps the work item's `UpdatedAtUtc`, inside a transaction. That statement holds the item's row until the transaction ends, so the link writes of one item run one at a time and two identical adds never meet on the unique key: the second waits, finds the first one's row and inserts nothing (its stamp is rolled back). Adding a comment writes in the same order, stamp first and then the `INSERT`; in the other order two writers of one item deadlocked (error 1213) on the shared lock the `INSERT` takes for its foreign key.

`006` changes `WorkItemComments`: `Author` grows from 80 to 320 characters (the length of a claimant name), and two nullable columns are added. `AuthorUserId` is the `AppUsers.Id` behind the token that wrote the comment; it has no foreign key, so a comment outlives its author, and it is `NULL` for every existing comment and for comments written without a token. `IdempotencyKeyHash` is the SHA-256, in lowercase hex, of the author's user id and the caller's idempotency key (the key itself is not stored, and a hash compares exactly where the default collation would ignore case); the unique key (`WorkItemId`, `IdempotencyKeyHash`) allows one comment per item and key and any number without a key (`NULL`). Existing rows are not rewritten: they keep their ids, authors and timestamps. It is safe to re-run.

The API writes a comment like a link: the `UPDATE` that stamps the item comes first and holds the item's row, then it looks for the idempotency key, reads the time of the item's latest comment, and inserts. Concurrent adds with one key therefore never meet on the unique key: the later ones wait, find the first one's row and insert nothing. Because comment writes of one item run one at a time, each comment also gets a `CreatedAtUtc` later than the latest one already stored (that time plus one microsecond when the writer's clock is not ahead of it, with the item stamped again to match), which is what lets `list_work_item_comments` page by (`CreatedAtUtc`, `Id`) without a new comment landing behind a reader's cursor. Comments inserted by hand are not covered by that rule, and one stored with a time far in the future pulls the later comments of its item, and the item's `UpdatedAtUtc`, forward with it.

`007` adds three nullable columns to `Projects`; existing projects keep their rows and get `NULL` in all three. `RepositoryUrl` (up to 2048 characters) is the http, https or ssh URL of the repository the project's work is done in, and `DefaultBranch` (up to 255 characters) the branch of it that work starts from. The API validates both on write (no credentials in the URL, a branch name git accepts), so do not set them by hand to values it would refuse. `IdempotencyKeyHash` is the SHA-256, in lowercase hex, of the creating caller's user id and idempotency key, as for comments; the unique key `IX_Projects_IdempotencyKeyHash` allows one project per key and any number without one (`NULL`). It is safe to re-run.

A project has no parent row to lock, so the API serialises creates that carry an idempotency key with the MariaDB named lock `kanban_project_creates` (`GET_LOCK`, 10 s timeout), the same way as dependency adds: the look-up of the key and the `INSERT` of two concurrent creates cannot interleave, the later one finds the first one's project, and the unique key is never hit. A keyed create that waits the full 10 s is refused with HTTP 503 and code `busy`, and writes nothing. Creates without a key take no lock.

`008` changes `WorkItems`: `Labels` grows from 240 to 4000 characters, and `Version` (`bigint NOT NULL DEFAULT 1`) is added. `Labels` is still one comma-separated string without spaces around the commas, so the labels already stored are kept as they are and the label filter of `GET /api/items` (`LOCATE` of `,label,` in the lowered, comma-wrapped string) is unchanged. Every existing item gets version 1, like a new item. It is safe to re-run.

`Version` counts the writes to an item's own fields. The API only ever writes it as `Version = Version + 1` inside an `UPDATE`, never from a value it read, so two writes cannot give an item the same version; do not set it by hand to a lower value. An update starts a transaction with `UPDATE WorkItems SET Version = Version + 1, UpdatedAtUtc = … WHERE Id = … [AND Version = …]`: that statement decides an `expected_version` (no row matched means HTTP 409 `conflict` and nothing written) and holds the item's row until the transaction ends, so the updates of one item run one at a time and each reads the item only after the one before it committed. A move is the same single conditional `UPDATE`, which also sets `Status` and `Order`, and in the same transaction a save that renumbers the siblings it displaces and writes only their `Order` (not their `Version` or `UpdatedAtUtc`). A move that is refused, or that fails, is rolled back whole.

Every write that gives an item a place in a column, or takes one out of it, starts its transaction with `UPDATE Projects SET IsArchived = IsArchived WHERE Id = …`, which changes nothing and holds the row of the item's project until the transaction ends: a move, an update that names a status (it may put the item at the end of another column), a create of a work item, an import of a plan, a delete of a work item and a delete of the project (before its items' rows). Those writes therefore run one at a time per project, and because the `UPDATE` is the first statement of the transaction, the reads after it (the end of the column, the siblings to renumber) see everything the earlier holders committed (`REPEATABLE READ` fixes the view at the first read). So no two items of one column of a project get the same `Order`, however many callers move, update, create and import at once, and a move never finds a sibling it read deleted by a delete of that item or of the project before it renumbers it. Should a sibling's row go some other way, the save that renumbers it matches no row (`DbUpdateConcurrencyException`): the move is rolled back whole and run again like the victim of a deadlock, up to three times in all, and then answered HTTP 503 `busy`. Taking an item out of an epic (archiving or deleting the epic) changes neither `Status` nor `Order`, but takes the project's row as well, then the epic's row (`UPDATE Epics SET IsArchived = IsArchived WHERE Id = …`), then the items: a write that puts an item into the epic reads the epic's row for its foreign key and then adds to `IX_WorkItems_EpicId`, and an archive that took the items first and the epic's row last deadlocked with it (error 1213). For the same reason an update that names an epic (to set or to clear it) takes the project's row first, like one that names a status: it holds the item's row when its save reads the epic's row. Columns that held two items with one `Order` before this are not renumbered by a migration: the next move into or within such a column renumbers all of it. The project of the item is read before the transaction starts (a project id never changes). The locks are taken in one order everywhere: the project's row, then (archiving or deleting an epic) the epic's row, then rows of `WorkItems`, then the named lock of the change feed. An update that names neither a status nor an epic does not take the project's row. Claims, comments, links and dependencies do not touch `Version`.

`009` adds the `WorkItemChanges` table, the change feed behind `list_changes`: one row per change to a work item. `Sequence` (`bigint AUTO_INCREMENT`, the primary key) is the position in the feed; `WorkItemId` and `ProjectId` name the item and its project; `Kind` is the kind of change; `ActorUserId` and `ActorName` are the user behind the token or the browser session that made it (both `NULL` when the request carried neither); `Changes` is a JSON array of `{"field", "old", "new"}`; `CreatedAtUtc` is the time of the write. `IX_WorkItemChanges_ProjectId_Sequence` serves a feed filtered by project. There is no foreign key on purpose: a row stays when its work item or its project is deleted, and nothing ever updates or deletes a row. Existing data is not touched and gets no rows: the feed starts with the first write after the migration. The table grows by one row per write and is not pruned. It is safe to re-run.

Every write to a work item now runs in a transaction that ends with the `INSERT` of its row here, so the row is stored exactly when the write is. The writes that used to be one statement (claim, renew, release, create, delete) are now a transaction as well. A write whose own `UPDATE` is conditional or overwrites what the row has to report (a claim, a move, a delete, taking items out of an epic) starts with `UPDATE WorkItems SET Version = Version WHERE Id = …`: it changes nothing, but it holds the item's row, so the `SELECT` after it returns the values the write then replaces, and no other writer can change them in between. The conditional `UPDATE` of a claim or of a guarded update still decides the winner. The item's row is always taken first and rows of other tables are written after it, as before.

The dependency writes now follow that rule too. An add starts, inside its named lock, with `UPDATE WorkItems SET Version = Version WHERE Id = … OR Id = …`, which holds the rows of both items in the order of their keys; before, its `INSERT` took a shared lock on each of the two rows for its foreign keys, one after the other, and deadlocked (error 1213, answered as HTTP 500) with a move that was renumbering the same two items in the other order. A remove starts by holding the row of the blocked item, so two removes of one edge run one after the other and the second finds nothing to delete. A delete of an item, or of its project, removes the edges in which a deleted item blocks another one through `ON DELETE CASCADE`; the delete records each of them that leaves an item behind as a `dependency_removed` row on that item. For that it holds those edges before its first `SELECT`, right after the item rows: `UPDATE WorkItemDependencies SET BlockerItemId = BlockerItemId WHERE BlockerItemId = …` for an item, and for a project `UPDATE WorkItems AS i STRAIGHT_JOIN WorkItemDependencies AS d ON d.BlockerItemId = i.Id SET d.BlockerItemId = d.BlockerItemId WHERE i.ProjectId = …`, which starts from the project's items (already held) and reaches the edges through `IX_WorkItemDependencies_BlockerItemId`, so no other edge and no item of another project is locked. A remove of one of those edges that runs at the same time then either commits first and is not seen, or waits and finds nothing to delete: the removal is recorded once.

A text in `Changes` is cut to 16,384 characters (see the README): an update of a 9 MB description would otherwise put 18 MB in one row, more than the default `max_allowed_packet` of 16 MB, and fail.

Deleting a project, and archiving or deleting an epic, hold the rows of several items with one statement and can be chosen as the victim of a deadlock (error 1213) by writers that hold one of those rows and wait for another. So can the writer on the other side: a move, an update or a delete of one item holds the item's row and then rewrites its entries in the indexes on `(ProjectId, Status, Order)` and `EpicId`, which the statement of the other transaction reached first; an add of a dependency holds the rows of two items in the order of their keys, not of that index; a remove of a dependency deletes the edge's row and then its entry in the index on `BlockerItemId`, through which a delete of the blocking item holds it. All of these (`move`, update, delete, create of a work item, add and remove of a dependency) are run again in the same way. A claim, a renewal, a release, a comment and a link add or remove are not: each holds the row of one item, writes no indexed column of `WorkItems` and no row another transaction reaches before that item's row, so once it holds the row it waits for no row lock and cannot be part of a cycle. The API runs such a transaction again, up to three times in all, and then answers HTTP 503 with code `busy`.

`010` makes the creation of epics, epic documents and work items repeatable and adds the record of an epic plan import. `WorkItems`, `Epics` and `EpicDocuments` each get a nullable `IdempotencyKeyHash` (the SHA-256, in lowercase hex, of the creating caller's user id and idempotency key, as for comments and projects) under a unique key: (`ProjectId`, `IdempotencyKeyHash`) on `WorkItems` and on `Epics`, (`EpicId`, `IdempotencyKeyHash`) on `EpicDocuments`. Existing rows keep `NULL`, and a unique key admits any number of `NULL`s, so rows created without a key never collide. `EpicPlanImports` holds one row per `import_epic_plan` call that created an epic: `EpicId` (the primary key, referencing `Epics.Id` with `ON DELETE CASCADE`, so the row and with it the key go with the epic), `ProjectId`, `IdempotencyKeyHash` (unique per project) and `Result`, the JSON of the document ids and of the item id of every `ref` as the import answered them. A repeat of the key answers from `Result`, not from the board; do not insert or edit these rows by hand. It is safe to re-run.

`011` adds `AppUsers.DisabledAtUtc` (`datetime(6) NULL`): when a service identity was disabled from the Admin page, `NULL` while it is enabled and for every person. Existing rows keep `NULL`. A disable sets it and revokes the identity's tokens in one transaction that starts with `UPDATE AppUsers SET DisabledAtUtc = DisabledAtUtc WHERE Id = …`; an issue from the Admin page and `create-service-identity` start with the same `UPDATE`, so an issue and a disable of one identity run one after the other and no unrevoked token is left on a disabled identity. Do not set it by hand without revoking the identity's tokens. It is safe to re-run.

`012` adds four nullable columns to `PersonalAccessTokens`: `IssuedByUserId` (`varchar(36)`) and `IssuedByName` (`varchar(320)`), the admin who issued the token from the Admin page (an issue, or the replacement of a rotate), and `RevokedByUserId` / `RevokedByName`, the admin who revoked it there (a revoke, the token a rotate replaces, each token a disable revokes). Like a change-feed entry's actor they keep the user's id and name at that moment and have no foreign key. A second revoke keeps the first revoker, as it keeps the first revocation time. Existing tokens, and tokens issued or revoked by `create-service-identity` or on the Settings page, keep `NULL`. It is safe to re-run.

`013` adds `IX_WorkItemChanges_WorkItemId_Sequence` on `WorkItemChanges` (`WorkItemId`, `Sequence`), which serves the history of one work item: `GET /api/items/changes?itemId=…` (the Story page) and `list_changes` with `item_id`. Without it such a read scans the whole feed. Existing rows are not changed. It is safe to re-run.

A keyed create and an import need the look-up of the key and the `INSERT` to run one caller at a time, and both have a parent row to do it with. Their transaction starts with an `UPDATE` that changes nothing: `UPDATE Projects SET IsArchived = IsArchived WHERE Id = …` for an epic, a work item and an import, `UPDATE Epics SET IsArchived = IsArchived WHERE Id = …` for a document. It holds the parent's row until the transaction ends, and because it comes before the first read, the look-up that follows sees what the earlier holders committed (under REPEATABLE READ a read before it would not). The second of two calls with one key therefore waits, finds the first one's row and inserts nothing, and the unique key is not hit. Should it be hit all the same (error 1062 naming one of the four indexes above), the API rolls back and looks the key up again outside the transaction, where the row that won is visible, and answers with it; any other duplicate entry is an error. A create of a work item without a key starts with the same `UPDATE Projects …` and then reads `MAX(Order)` of its column: read before it, or outside the transaction, several creates at once read the same end and took the same `Order` (as did an import beside them). An `INSERT` of another child row (an epic without a key) takes a shared lock on the same parent row for its foreign key, so it waits for a keyed create or an import in the same project and does not deadlock with it: it holds nothing when it waits. A `delete_project` can deadlock with an import or a create of a work item into that project (it holds the index range of the project's items and waits for the project's row, the import the other way round); both are run again up to three times, like the deletes above, and the one that comes second finds the project gone and answers `not_found`.

An import writes the epic, the documents, the items, the dependencies and its `EpicPlanImports` row with one `SaveChanges` (parents before children, the dependencies after the items they name) and only then takes `kanban_work_item_changes` for the `INSERT` of its entries (one per item, then one per dependency) and the `COMMIT`. The largest plan (200 items, 20 documents, 500 dependencies, 1.9 MB of JSON) took about 150 ms against a local MariaDB 11.4, a plan of the same counts with short texts about 90 ms; writes to other items waited at most 85 ms for it, and creates in the same project at most 150 ms.

The order of the feed is what a reader relies on: having read up to sequence N, it must never find a new row at or below N. `AUTO_INCREMENT` alone does not give that, because a transaction that took N can commit after one that took N+1. So the API inserts and commits the row while it holds the MariaDB named lock `kanban_work_item_changes` (`GET_LOCK`, 10 s timeout), which it releases on the same connection after the `COMMIT`: rows are numbered and committed one writer at a time, in the same order. The lock is taken last, after every row lock of the write, and its holder waits for nothing but its own `INSERT` and `COMMIT`, so it cannot be part of a deadlock; a dependency add holds it inside `kanban_work_item_dependencies`. The price is that writes to work items commit one after the other; the lock is held for three statements (`INSERT`, `COMMIT`, `RELEASE_LOCK`), so the API as a whole records at most one entry per three round trips to the database. Against a local `mariadb:11.4`, 48 concurrent writers spread over 16 items completed about 250 writes per second with the feed and about 550 without it; writers of one item, which wait for each other anyway, about 115 and 210. `SELECT IS_USED_LOCK('kanban_work_item_changes')` shows a holder. A write that waits the full 10 s is refused with HTTP 503 and code `busy`, and its transaction is rolled back. Do not insert rows by hand: a row inserted without the lock can land behind a reader's cursor. The order was checked against a real server with 48 writers and five readers polling `list_changes` without pause: every reader ended with exactly the committed rows, each once and in order, and with the lock taken out of the code the same test lost rows on every run. The same runs pass with `innodb_snapshot_isolation=ON` (the default of later MariaDB versions): the scheme reads nothing under the lock, so there is no row it could find changed.

`001` creates the EF migrations history table and the initial Kanban schema:

- `Projects`
- `AppUsers`
- `Epics`
- `EpicDocuments`
- `WorkItems`
- `WorkItemComments`
- `PersonalAccessTokens`

MariaDB note: `MySql.EntityFrameworkCore` takes the migration lock with `GET_LOCK('__EFMigrationsLock',-1)`, which MariaDB rejects, and reads the result as a MySQL `BIGINT` while MariaDB returns `INT`. `MariaDbMigrationLockInterceptor` rewrites that one statement to a positive timeout and widens the result. It is registered on the API's `DbContext` and on the design-time factory (`dotnet ef database update`). The provider also ignores the `GET_LOCK` result, so it would migrate after a timed-out wait (result `0`) while another session still held the lock; the interceptor throws a `TimeoutException` for any result other than `1`. The lock wait (default 600 s) is kept 60 s below the migration command timeout (`Database:MigrationCommandTimeoutSeconds`, default 660 s): if the client timed out first, MariaDB would keep the lock on the killed connection and the API would hang. `StartupMigrationTests` covers the rewrite, the timeout result and the command timeout through the EF Core pipeline (sync and async) with a faked connection. Against a real `mariadb:11.4` server it was also checked by hand: with another session holding the lock for 75 s the API waited and then migrated, and with the lock held past the wait it exited with the `TimeoutException` and changed no schema.
